# VidiStudio Mac agent guide

Native SwiftUI macOS 26 plain app in `VidiStudio.xcodeproj`. `VidiStudio/` owns native UI and engine invocation. `engine/vidistudio_engine.py` owns all project processing and writes. The sibling VidiStudio Online repository is a visual/workflow reference, not a desktop runtime dependency. Website product documentation is part of desktop feature work as required below; unrelated online application changes require an explicit request. Preserve unrelated work.

## Required Help and website documentation synchronization

- Whenever a feature is added, changed, or removed in either the Mac or Windows app, update both desktop Help and the website documentation in the same task, without waiting for a separate documentation request. Documentation must describe the actual application behavior, labels, menu paths, shortcuts, defaults, limitations, and any genuine platform differences.
- Canonical desktop Help lives in `VidiStudio Mac/docs/help/*.html`. From the Mac checkout, run `python3 script/build_help.py`, then `python3 ../Vidi-Studio-Windows/script/sync_windows_help.py --mac-root .` to generate matching Windows Help. Edit the canonical sources rather than only the generated Windows pages.
- Update the website guide at `VidiStudio Online/src/pages/DocsPage.tsx` and every affected website feature, workflow, import/export, FAQ, shortcut, troubleshooting, or privacy section. Correct outdated guidance throughout the existing documentation as well as documenting the new behavior.
- Validate Help generation and links, website checks/build, and affected documentation navigation or search. Keep installed Help and the published website aligned with shipped application features. Record build, installation, or publication blockers in `PROGRESS.md` and the task handoff; distinguish edited sources, generated output, installed Help, and live website publication when reporting completion.

Project data lives in portable local folders with relative paths. Credentials live only in the user config outside projects. No Firebase, Firestore, authentication or embedded website. Gemini runs only in the Python engine; keep API keys out of argv, logs and project JSON. Files API uploads need bounded readiness polling and cleanup.

Use native macOS controls with bundled Material Symbols for application iconography; system-owned chrome retains Apple icons. Shared AI settings use the online model/prompt schema. Preserve labels, keyboard access, visible focus and VoiceOver names. Liquid Glass comes from the system sidebar, toolbar and controls. Avoid painting custom opaque layers over them.

## Required desktop menu synchronization

The Mac menu layout is the reference for both desktop apps. Any menu or context/action-menu item added, removed, moved, renamed, re-keyed, or re-gated here **or on Windows** must be mirrored on the other platform in the same task. Preserve hierarchy/order/separators, labels/dynamic titles, enabled/checked state, command behavior, and equivalent shortcuts. Mirror stable IDs between `VidiStudio/KeyboardShortcuts.swift` / `VidiStudioApp.swift` and Windows `MainWindow.Menus.cs`; menu activation and keyboard shortcuts must share the same guarded action. Keep native OS app/Edit/Window conventions, and document genuine platform exceptions in `docs/DESKTOP_MENU_PARITY.md` on both sides. Run `python3 script/check_menu_parity.py` and `python3 -m unittest tests.test_menu_parity` from each desktop checkout with the combined workspace present. Build and pre-commit scripts also run the checker; a standalone skip is not evidence of cross-platform validation. Update the checker and native smoke expectations when adding a new menu construct, and never complete a one-platform menu change without its counterpart or an explicit OS-specific exception.

Run `script/build_and_run.sh --verify` for build and launch. Direct Xcode builds run `script/xcode_bundle_engine.sh`. `script/package.sh` creates a local-install ZIP. Python dependency versions used for validation are in `engine/requirements-build.lock`. `tests/test_engine.py` exercises real media processing and system speech; it needs OS speech access outside restricted sandboxes.

## Installed app updates

Every Mac app update includes the Share extension (used by Safari/Finder sharing) and Finder extension. Keep both targets' marketing version/build equal to the app, embed them in the replacement installation, and sign all three with the same stable Apple Development identity/team and their canonical entitlements. Never switch an extension to ad hoc signing. `script/build_and_run.sh` verifies versions, signatures, entitlements and compatibility with the previous installation's designated requirements before replacement; it stops old extension processes, removes build-path registrations, registers the installed extensions, and verifies that PlugInKit lists one current instance of each under `/Applications/VidiStudio.app`. Preserve the user's extension enable/disable choices. Run `python3 script/verify_extensions.py /Applications/VidiStudio.app --registered` and record app/extension versions, signing continuity and registration evidence in `PROGRESS.md` on every release. Validate Safari Share to VidiStudio when changing sharing or extension installation; distinguish a verified launch from a completed import.

The macOS “differs from previously opened versions” warning is container identity protection, not a version-number check. An old unsigned/ad hoc container can require a one-time user approval even after stable signing is restored. Diagnose signatures and container ownership read-only; do not delete containers, edit ownership metadata, reset privacy permissions or disable protections to suppress it. Explain any remaining approval and let the user approve the verified updated extension. Keep Help and website troubleshooting aligned with this behavior.

`script/build_and_run.sh` builds into `build/DerivedData.noindex` and, for every mode except `--build-only`, installs the signed app over `/Applications/VidiStudio.app`, deletes the build product, and unregisters it from LaunchServices. `--build-only` keeps the signed product for `script/package.sh` but unregisters it. Installing must replace the previous copy: never launch or leave duplicate `VidiStudio.app` bundles in `/Applications`, `~/Applications`, `dist`, the Bin, or DerivedData/build folders. After installing, confirm `mdfind -name VidiStudio.app` and the LaunchServices dump list only the current `/Applications/VidiStudio.app`.

Install on every version update. After bumping the version, run `script/build_and_run.sh --verify` (or `run`) so `/Applications/VidiStudio.app` is replaced and reports the new version; a version bump is not complete until the installed copy is updated, only one app is discoverable, and the install evidence is in `PROGRESS.md`.

App versioning between macOS (`VidiStudio Mac`) and Windows (`Vidi-Studio-Windows`) must always remain strictly in sync. Every app fix or new feature must automatically advance the app version across both platforms before build and validation; do not wait for a separate version-bump request. Run `python3 script/sync_version.py --bump` to atomically increment the patch version across both macOS (`MARKETING_VERSION` and `CURRENT_PROJECT_VERSION` in `VidiStudio.xcodeproj/project.pbxproj`) and Windows (`<Version>` in `Vidi Studio Windows.csproj` and `Version` in `Package.appxmanifest`). If editing versions manually, ensure both platforms are updated to the exact same version `1.0.X` (with Windows package `1.0.X.0` and Mac build number aligned). The build scripts (`script/build_and_run.sh`, `script/xcode_bundle_engine.sh`), pre-commit hooks, and parity tests (`tests/test_parity.py`) automatically run `sync_version.py --sync` to maintain version parity. Record the resulting user-visible version and build number in `PROGRESS.md` with the change's validation evidence.

Use `VIDISTUDIO_TEST_ENGINE` to test the packaged executable. Do not claim live Gemini or Windows validation without actually running those paths. Record progress and release evidence in `PROGRESS.md`.

## Xcode MCP

This Mac configures Xcode's MCP server for local ChatGPT and Codex clients as `xcode`, using `xcrun mcpbridge`. When the Xcode MCP tools are available in a session, use them as the primary integration for inspecting and controlling the open `VidiStudio.xcodeproj`: Xcode-aware navigation, scheme and target inspection, compiler diagnostics, building, testing, running, debugging, and other capabilities exposed by Xcode belong on this path.

Before using Xcode MCP, verify that `VidiStudio.xcodeproj` is open in Xcode and that Xcode > Settings > Intelligence > Model Context Protocol > Allow external agents to use Xcode tools is enabled. If the server is configured but its tools are absent from the current agent session, report that the local ChatGPT/Codex client needs to restart or begin a new session; do not claim Xcode MCP control from configuration alone.

Xcode MCP complements rather than replaces repository validation. Continue to run `script/build_and_run.sh --verify` for the required packaged build and launch, run packaged-engine tests with `VIDISTUDIO_TEST_ENGINE`, and record the exact evidence in `PROGRESS.md`. Treat Xcode MCP build, run, preview, and diagnostic results as distinct from script packaging, engine tests, live Gemini execution, Windows validation, commit, and push evidence.

## Concise application UI copy

Keep explanatory descriptions, workflow instructions, and detailed behavior guidance in canonical desktop Help and website documentation. Do not add instructional paragraphs, explanatory footers, or long descriptions to Settings, Project Settings, inspectors, or application dialogs (including Import, Export, Delete, and generation/review dialogs). Use concise control labels and necessary action buttons. Retain short errors, validation states, affected item/file counts, required legal notices, and essential confirmation details. Preserve accessible control names and icon-action tooltips, without putting long procedural guidance there. When behavior changes, update Help and website documentation instead of expanding the application UI copy.


## Required menu access for every new UI action

Every new UI action anywhere in this application—including text/icon buttons, toolbar/sidebar/inspector actions, toggles, pickers, navigation/view controls, and Settings/dialog actions—must have a corresponding context-appropriate menu entry in the same task. Menus must expose the same action, navigation destination, toggle or choice, checked state, dynamic title, availability and confirmations through the same guarded path and shared state. Scope entries to the active window, section, dialog and visible selection. Mirror shared entries on the other desktop and update parity checks, native smoke/regression coverage, Help and website documentation. Follow the workspace AGENTS.md section “UI Actions Must Be Available from Menus (Required)” and record any runtime validation blocker; a new UI control without its menu path is incomplete.
